# REG-06 Glossary and Terminology

> Part of [[README]] | See also: [[REG-01 Compliance Matrix]], [[PH-07 GxP Validation Documentation]]

Reference glossary covering all three technical vocabularies used in this project: GxP/regulatory terms, bioinformatics terms, and Kubernetes/infrastructure terms. Intended for cross-functional readers who are expert in one domain but not the others.

---

## GxP and Regulatory Terms

**21 CFR Part 11**
US FDA regulation (Code of Federal Regulations, Title 21, Part 11) governing electronic records and electronic signatures in pharmaceutical manufacturing and development. Requires audit trails, access controls, and validation of computer systems. The US equivalent of EU GMP Annex 11.

**Annex 11**
EU GMP (Good Manufacturing Practice) Annex 11: Computerised Systems. A regulatory guideline from the European Medicines Agency (EMA) that defines how computer systems used in pharmaceutical manufacturing and development must be validated, secured, and operated. Published 2011, currently in revision.

**Audit Trail**
A chronological record of who did what to which data, at what time, and from where. In a computer system context, an audit trail is tamper-evident (cannot be deleted or modified by the operator of the system being audited). In this platform, the audit trail is generated by Falco at the kernel level and stored in Loki on MinIO with bucket lock enabled.

**Change Control**
A formal process for managing changes to a validated system. Requires a documented request, impact assessment, approval before implementation, and a record that the change was made. In this platform, the Forgejo PR workflow is the change control mechanism -- no change reaches the cluster without a traceable Git commit.

**COTS (Commercial Off-The-Shelf)**
Pre-built software purchased or obtained from an external source and used without modification. In GAMP 5, COTS maps to Category 3 (non-configured) or Category 4 (configured). Prometheus, Grafana, and Talos are COTS in this context.

**GAMP 5**
Good Automated Manufacturing Practice, 5th edition. An industry validation methodology published by ISPE (International Society for Pharmaceutical Engineering). Defines five software categories (1-5) with increasing validation requirements. This platform's configurations are Category 4 (configured software). nf-core/rnaseq is treated as Category 5 (custom software) because we configure and validate it ourselves.

**GAMP 5 Category 4**
Configured software. The underlying software (Kubernetes, Helm charts) is provided by a vendor but the configuration is ours. The validation scope covers the configuration -- our Rego policies, Falco rules, Nextflow config, Helm values. Not the underlying code.

**GMP (Good Manufacturing Practice)**
A system of regulations and guidelines governing the manufacture of pharmaceutical products. Ensures that products are consistently produced and controlled according to quality standards. GxP is the broader umbrella term covering GMP plus GCP (clinical), GLP (laboratory), and GDP (distribution).

**GxP**
Abbreviation for "Good x Practice" where x represents the regulated activity (Manufacturing, Clinical, Laboratory, Distribution). GxP systems are computer systems that support regulated activities and are therefore subject to validation and audit requirements.

**IQ (Installation Qualification)**
The first of three validation phases. Documents that a system was installed correctly, that all components are present at the correct versions, and that the installation matches the specification. Answers: "Did we install what we said we would install?"

**OQ (Operational Qualification)**
The second validation phase. Tests that the installed system functions as designed through scripted test cases with defined pass/fail criteria. Answers: "Does the system do what it is supposed to do?"

**PQ (Performance Qualification)**
The third validation phase. Tests that the system performs at the required level under realistic conditions. For this platform, PQ means running the nf-core/rnaseq pipeline twice and confirming reproducible results. Answers: "Does the system perform acceptably in production conditions?"

**Regulatory Submission**
Data submitted to a health authority (FDA, EMA) as part of a drug approval application. If the computational systems that generated or processed the data were not validated, the submission may be rejected.

**SOP (Standard Operating Procedure)**
A documented step-by-step procedure for performing a specific operational task. SOPs are required evidence in GxP environments. In this platform, SOPs cover change control, access control, backup and recovery, and audit trail management.

**Statement of Applicability (SoA)**
A mandatory document in ISO 27001 that lists every control in Annex A, states whether it applies to the scope, provides justification, and references the evidence. Cannot be omitted from an ISO 27001 certification claim. See [[REG-05 Statement of Applicability]].

**Validation**
The process of establishing documented evidence that a system consistently meets its intended use requirements. In GxP, validation is not optional -- it is the mechanism by which a computer system earns the right to be used in a regulated process.

## Bioinformatics Terms

**Alignment (Sequence Alignment)**
The process of mapping short DNA or RNA reads from a sequencing experiment to a reference genome. In RNA-seq, the STAR aligner maps reads to the genome to determine which genes they came from. The alignment step is computationally intensive and is where most of the CPU and RAM load in a pipeline run originates.

**BAM/SAM File**
Binary Alignment Map / Sequence Alignment Map. File formats for storing aligned sequencing reads. BAM is the compressed binary version of SAM. These are large files (often several gigabytes per sample) and are the primary output of the alignment step. Stored in the pipeline-output MinIO bucket.

**Bioinformatics**
The application of computational methods to biological data. In the context of drug development, bioinformatics is used to analyse genomic and transcriptomic data from clinical trials, biomarker discovery, and target identification.

**FASTQ**
A text-based file format for storing raw sequencing reads from a sequencing instrument. Contains the nucleotide sequence and a quality score for each base. The primary input to an RNA-seq pipeline. Files are typically provided to the pipeline via the pipeline-input MinIO bucket.

**MultiQC**
A tool that aggregates quality control reports from multiple bioinformatics tools into a single HTML report. In nf-core/rnaseq, MultiQC is the final step and produces the report used as the PQ reproducibility reference (the MD5 checksum of the MultiQC HTML must match across two independent runs).

**nf-core**
A community of bioinformaticians who develop and maintain standardised, peer-reviewed Nextflow pipelines for common bioinformatics analyses. nf-core pipelines follow consistent design principles and are widely used in pharmaceutical research. See https://nf-co.re.

**nf-core/rnaseq**
The nf-core RNA sequencing analysis pipeline. Performs quality control, trimming, alignment, quantification, and reporting on RNA-seq data. The specific pipeline validated in this project. GAMP 5 Category 5 in this context.

**Nextflow**
A workflow management system for bioinformatics. Uses a domain-specific language (DSL) to define pipelines as directed acyclic graphs of processes. Each process runs in a container. Nextflow orchestrates container execution -- on this platform it uses the Kubernetes executor to submit containers as K8s pods.

**RNA-seq (RNA Sequencing)**
A sequencing technology that measures gene expression levels across the genome. Used in pharmaceutical research to understand how drugs affect gene activity, for biomarker discovery, and for target identification in early drug development. nf-core/rnaseq is the pipeline that processes raw RNA-seq data.

**Reference Genome**
The assembled DNA sequence of a species used as a reference for alignment. For human RNA-seq, the reference is GRCh38 (human genome assembly 38). Nextflow downloads the reference genome automatically for the test profile.

**Read Trimming**
Removing low-quality bases and adapter sequences from the ends of raw sequencing reads before alignment. Performed by tools like Trim Galore in nf-core/rnaseq. Improves alignment accuracy.

**STAR**
Spliced Transcripts Alignment to a Reference. The aligner used by nf-core/rnaseq to map RNA-seq reads to the genome. Memory-intensive -- requires approximately 30-40GB RAM for a full human genome run. The test profile uses a small subset and requires much less.

**Test Profile**
In nf-core pipelines, the test profile runs the pipeline against a small, publicly available dataset that fits in limited compute and storage. Used for OQ validation because it runs in minutes and produces deterministic output without using any real patient data.

## Kubernetes and Infrastructure Terms

**Admission Controller**
A Kubernetes API server plugin that intercepts requests before objects are persisted in etcd. Can allow, deny, or mutate the request. OPA Gatekeeper installs a ValidatingAdmissionWebhook that evaluates policy rules on every CREATE and UPDATE request. If Gatekeeper denies the request, the pod is never created.

**ArgoCD**
A GitOps continuous delivery tool for Kubernetes. Watches a Git repository and continuously reconciles the cluster state to match what is defined in Git. ArgoCD is the change management enforcement mechanism on this platform -- any manual change to the cluster is detected and reverted.

**CGNAT (Carrier-Grade NAT)**
A form of network address translation used by ISPs to share a single public IP across many customers. DU Telecom uses CGNAT for this connection. The consequence is no inbound port forwarding is possible -- all external access must be outbound-initiated (which is what Cloudflare Tunnel does).

**Cert-Manager**
A Kubernetes operator that automates TLS certificate provisioning and renewal. Configured with a ClusterIssuer (in this case a self-signed CA), Cert-Manager issues certificates for every Ingress object and renews them automatically 30 days before expiry.

**CNI (Container Network Interface)**
The plugin that handles pod networking on Kubernetes. Responsible for assigning IP addresses to pods and managing routing. Flannel is the current CNI -- it does not enforce NetworkPolicy objects. Cilium is the planned replacement and does enforce NetworkPolicy.

**ConfigMap**
A Kubernetes object for storing non-sensitive configuration data as key-value pairs. Mounted into pods as environment variables or files. Falco's custom rules are loaded via a ConfigMap.

**CRD (Custom Resource Definition)**
An extension mechanism in Kubernetes that allows defining new resource types beyond the built-in ones. OPA Gatekeeper uses CRDs to define ConstraintTemplates and Constraints. Cert-Manager uses CRDs for Certificates and ClusterIssuers.

**DaemonSet**
A Kubernetes workload type that ensures exactly one pod runs on every node (or every node matching a selector). Falco and Promtail run as DaemonSets to ensure every node has runtime monitoring and log collection regardless of what workloads are scheduled on it.

**eBPF (Extended Berkeley Packet Filter)**
A Linux kernel technology that allows running sandboxed programs inside the kernel without changing kernel source code. Falco uses eBPF to hook into kernel system calls -- this is why Falco can see everything containers do (file access, network connections, process execution) without being able to be disabled from within a container.

**etcd**
A distributed key-value store used by Kubernetes to persist all cluster state: pod definitions, RBAC rules, secrets, ConfigMaps, and everything else. If etcd is lost, the cluster state is lost. etcd snapshots are the backup mechanism. Talos manages etcd internally.

**Flannel**
A simple CNI plugin that provides overlay networking for Kubernetes pods. Does not enforce NetworkPolicy objects. Used here as the initial CNI because it was already deployed. Cilium migration is planned post-CKA to enable NetworkPolicy enforcement.

**Helm**
A package manager for Kubernetes. Packages are called Charts. Helm templates Kubernetes manifests from values files and installs them as releases. All platform components are installed via Helm in this project.

**Ingress**
A Kubernetes API object that defines HTTP routing rules. Maps hostnames and paths to backend services. Ingress-NGINX is the controller that reads these objects and programs the NGINX proxy accordingly.

**kubectl**
The command-line tool for interacting with the Kubernetes API server. Reads cluster credentials from the kubeconfig file. All cluster operations outside of ArgoCD automation use kubectl.

**MetalLB**
A load balancer implementation for bare-metal Kubernetes clusters. In L2 mode, MetalLB responds to ARP requests on the LAN for the assigned IP address (192.168.0.200), directing traffic to the cluster. This is how services with type LoadBalancer get an accessible IP address without a cloud provider.

**Namespace**
A logical partition within a Kubernetes cluster. Resources in different namespaces are isolated by RBAC. In this project, each major component runs in its own namespace: argocd, monitoring, forgejo, authentik, minio, gatekeeper-system, pipelines.

**NodeSelector**
A pod scheduling constraint that restricts which nodes a pod can run on. Uses node labels to match. This project uses `node-role: storage` for Beelink and `node-role: infra` for Omen to enforce workload placement.

**OPA (Open Policy Agent)**
A general-purpose policy engine that uses a language called Rego to evaluate policies against JSON data. OPA Gatekeeper uses OPA to evaluate Kubernetes admission requests against policies defined as ConstraintTemplates.

**PersistentVolume (PV)**
A piece of storage that has been provisioned in the cluster. In this project, PVs are provisioned by local-path-provisioner on the Beelink HDD at /var/mnt/hdd.

**PersistentVolumeClaim (PVC)**
A request for storage by a pod. The PVC is bound to a PV by the storage provisioner. `WaitForFirstConsumer` binding mode means the PV is not created until a pod is scheduled -- this ensures the pod and PV are co-located on the same node.

**RBAC (Role-Based Access Control)**
A Kubernetes access control mechanism. Roles define what actions (verbs) are allowed on which resources. RoleBindings connect users or ServiceAccounts to Roles. In this project, the nextflow-runner ServiceAccount has a namespace-scoped Role (not ClusterRole) to limit what pipeline pods can do.

**Rego**
The policy language used by OPA and OPA Gatekeeper. Rego policies evaluate JSON input (a Kubernetes admission request) and return allow/deny decisions with violation messages. Rego is not portable to other policy systems like Kyverno -- converting policies requires a full rewrite.

**ResourceQuota**
A Kubernetes object that limits total resource consumption in a namespace. In this project, the pipelines namespace has a ResourceQuota limiting total CPU requests and memory requests. Prevents a pipeline from consuming all cluster resources.

**Sealed Secrets**
A Kubernetes controller and CLI tool (kubeseal) that allows encrypting secrets for safe storage in Git. The controller holds an RSA private key. kubeseal encrypts secrets using the controller's public key. Only the controller can decrypt them. Critical: back up the private key.

**ServiceAccount**
A Kubernetes identity for processes running inside pods. When a pod is created, it uses a ServiceAccount to authenticate to the K8s API server. The nextflow-runner ServiceAccount has only the permissions needed to run pipelines -- nothing more.

**StorageClass**
A Kubernetes object that defines how to provision storage. In this project, `local-hdd` is the default StorageClass, backed by local-path-provisioner on the Beelink HDD. `WaitForFirstConsumer` binding ensures PVs are created on the node where the requesting pod will run.

**Talos**
An immutable, minimal Linux OS purpose-built for Kubernetes. Has no shell, no SSH, no package manager. Managed entirely through the Talos API (talosctl). The immutable design means OS vulnerabilities cannot be exploited interactively -- there is no session to hijack.

**talosctl**
The command-line tool for managing Talos nodes. Used for upgrades, configuration patches, etcd snapshots, and health checks. Reads credentials from the talosconfig file.
